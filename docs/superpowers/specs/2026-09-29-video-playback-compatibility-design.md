# 作品视频播放兼容性修复设计

## 目标

修复线上所有作品视频点击“加载视频”后无法播放的问题，同时保留现有按需加载策略，避免页面打开时下载视频。

## 已确认原因

- 六个线上视频均存在，返回 `video/mp4`，并支持 HTTP Range 分段请求。
- 当前组件在点击后才挂载 `<video>`，同时依赖 `autoPlay` 启动播放。
- React 状态更新与元素重新挂载会让部分浏览器丢失本次点击的用户手势；配合 `preload="none"` 时，可能停留在加载状态或被浏览器阻止播放。

## 采用方案

### 稳定的原生播放流程

- `<video>` 从封面状态起就保留在 DOM 中，但使用 `preload="none"`，不提前下载视频。
- 封面和“加载视频”按钮覆盖在播放器上方，保持现有视觉表现。
- 用户点击按钮时，在同一个点击事件中直接调用 `video.load()` 与 `video.play()`，避免依赖重新挂载后的自动播放。
- 点击后立即显示原生控制条。若浏览器阻止自动播放，用户仍可通过原生播放按钮继续，而不会卡在不可操作状态。
- 播放成功后隐藏加载状态；等待数据时显示“视频加载中…”。
- 网络或解码失败时恢复封面并显示“重新加载”。

## 组件边界

- 仅修改 `DeferredVideo` 的播放状态与事件处理。
- `MediaViewer`、作品数据、视频路径、封面、弹层布局与视觉主题保持不变。
- 不引入第三方播放器、CDN、HLS 或新的运行时依赖。

## 状态模型

- `idle`：仅显示封面与加载按钮，视频不请求内容。
- `loading`：用户已触发加载，显示原生控制和加载提示。
- `ready`：视频已开始播放或已具备可播放数据。
- `error`：显示封面与重试按钮；重试会重新执行原生加载流程。

## 验证标准

- 打开作品查看器时，视频资源不会自动下载。
- 点击“加载视频”后，浏览器立即发起视频请求，并显示可操作的原生控制条。
- 自动播放受限时不会卡死，用户可以再次点击原生播放键。
- 六个项目视频在本地生产构建中都能开始播放。
- GitHub Pages 上的视频路径继续返回 `206 Partial Content`。
- 现有视频加载验证、桌面体验验证、代码检查与生产构建全部通过。

## 不在本次范围

- 不重新压缩视频。
- 不修改项目卡片或查看器排版。
- 不迁移视频托管平台。
